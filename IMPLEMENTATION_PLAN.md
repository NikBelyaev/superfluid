# План реализации Superfluid

Дата: 5 ноября 2026 года. Статус: проект реализации до начала разработки.

Superfluid — локальная IDE для Python на Electron, в которой несколько worktree одного или нескольких проектов остаются самостоятельными рабочими сессиями. Главный критерий качества — возможность немедленно продолжить работу после любого переключения, в том числе пока другая ветка выполняет тесты, сервер пишет логи, Git обновляет состояние, а language server анализирует импорты.

Первый релиз использует GitHub — это подтверждено пользователем. Основная платформа по рабочему допущению — macOS Apple Silicon. Windows и Linux не должны блокировать проектирование границ, но их выпуск требует отдельных проверок PTY, файловой системы, горячих клавиш и упаковки. GitLab/MR — за пределами v1.

Все численные бюджеты ниже — предлагаемые критерии приемки, а не результаты существующего приложения. Каталог Superfluid на момент планирования пустой.

## 1. Что входит в первый релиз

1. Экран проектов: недавние и закрепленные проекты, поиск, открытие папки, создание минимального Python-проекта, клонирование репозитория, вход в конкретный worktree.
2. Проектная рабочая область: дерево, редактор с вкладками, палитра команд, поиск файлов и текста, Python-навигация, диагностика, форматирование и выбор интерпретатора.
3. Работа с несколькими worktree: обнаружение существующих, создание новых, быстрый переход, независимые несохраненные документы, окружения, терминалы, процессы, раскладка и Lineage.
4. Плавающий остров: команды проекта, текущая ветка, Git-действия, изменения, серверы и именованные терминалы, история переходов по коду.
5. Вторая группа поверхностей справа: файлы, терминалы, браузер, diff и PR. Существующие вкладки можно переносить между двумя группами.
6. Локальные изменения: дерево измененных файлов, staged/unstaged/untracked, просмотр diff, выбор файлов для commit, commit/push/create PR отдельно и одной последовательностью.
7. GitHub PR: Summary, Timeline, Code, проверки, обсуждения, переход из измененной строки в редактор; создание PR из текущей ветки.
8. Восстановление раскладки и черновиков после перезапуска, корректная работа без сети, измерение производительности и защита от ее регрессий.

Граница Git-функций следует исходному запросу: текущая ветка отображается отдельно, составная кнопка выполняет Commit → Push → PR. Создание новой ветки входит в отдельное действие создания worktree (§5.3); автоматический шаг Branch внутри публикации не требуется. Если текущий checkout — detached HEAD, публикация предлагает сначала явно создать именованную ветку/worktree или выбрать существующую сессию, сохраняя черновики исходной. Перенос несохраненных файлов между worktree не выполняется автоматически.

В v1 не включаем AI-чат, оркестрацию агентов, удаленные машины, Dev Containers, плагины, ноутбуки, собственный Python type checker, визуальный debugger, дизайнер БД и произвольное число docking-панелей. Python-скрипты и pytest запускаются в терминале. Графический debugger через DAP можно добавить после этого набора; создание собственной IDE не требует сразу воспроизводить все возможности PyCharm.

Слово «универсальная» означает общий механизм размещения перечисленных поверхностей. Оно не требует поддержки любых форматов документов в первом релизе.

## 2. Как использовать T3 Code

T3 Code уже имеет Electron-приложение и интерфейс на React/Vite. Сервер владеет файлами, Git и терминалами, клиент подключается через типизированный RPC. Это подходящая исходная граница для Superfluid. Проверены [описание архитектуры](https://github.com/pingdotgg/t3code/blob/main/docs/internals/overview.md), [зависимости UI](https://github.com/pingdotgg/t3code/blob/main/apps/web/package.json) и [Electron-пакет](https://github.com/pingdotgg/t3code/blob/main/apps/desktop/package.json).

Исследованный исходный commit: `337c5858c33bc7f8f6dfd391a2c279fa0f7e4d17`. При начале реализации сохраняем этот SHA, lockfile и происхождение перенесенных модулей. Обновления upstream переносим осознанно вместе с тестами. Не привязываем сборку к плавающему `main`.

Предлагаемый способ: самостоятельная кодовая база с сохранением привычной структуры T3 и переносом нужных модулей целиком с их существенными тестами. До первого большого переноса делаем короткий рабочий срез. Это позволит установить реальную цену зависимостей, особенно привязок к агентским `threadId`, авторизации, оркестратору и общему client-runtime.

| Область | Проверенный кандидат T3 Code | Решение для Superfluid |
|---|---|---|
| UI-примитивы | `apps/web/src/components/ui`, Base UI, Tailwind, Lucide | Перенести необходимый набор, использовать одинаковые меню, диалоги, focus management и resize handles |
| Git-контрол | `apps/web/src/components/GitActionsControl.tsx` | Перенести взаимодействия и проверенные состояния; заменить thread-контекст на явную рабочую сессию |
| Git-сервисы | `apps/server/src/git/GitManager.ts`, `GitWorkflowService.ts` | Использовать существующие операции и обработку ошибок; выделить минимальную независимую границу |
| Команды проекта | `ProjectScriptsControl.tsx`, `projectScriptEditor.tsx` | Взять список, форму и клавиатурное управление; убрать поля жизненного цикла агента |
| Терминалы | `apps/server/src/terminal/Manager.ts`, `ThreadTerminalDrawer.tsx` | Сохранить PTY lifecycle, ограничение истории и переподключение; привязать к worktree-сессии |
| Терминальный движок | Ghostty WASM, описанный в `terminal-runtime.md` | Переиспользовать parser и drawing/input adapters с ABI-проверкой; canonical parser в backend-worker — адаптация Superfluid, требующая проверки на этапе 0 |
| Diff | `apps/web/src/components/DiffPanel.tsx`, `@pierre/diffs` | Повторно использовать diff-движок и UI-паттерны, отделив их от чата |
| GitHub PR | `components/pullRequest/PullRequestDetailPanel.tsx`, `PullRequestCodeTab.tsx`, `packages/source-control-github` | Взять чтение PR, проверки и вкладки; адаптировать разрешения и идентификаторы |
| Пути | `apps/server/src/workspace/WorkspacePaths.ts` | Сохранить нормализацию и проверку выхода за корень рабочей области |
| Клиентское состояние | `@effect/atom-react`, отдельные части `packages/client-runtime` | Переиспользовать транспорт и точечные подписки, когда они отделимы от агентского домена |
| Полноценный редактор | `components/files/FilePreviewPanel.tsx` содержит редактируемую поверхность | Сопоставить с требованиями LSP/undo/multi-cursor; базовый выбор для IDE — Monaco |

Пути относятся к исследованному SHA; это кандидаты на адаптацию, не обещание подключить каждый файл без изменений. Сервис TerminalManager, например, имеет операции с `threadId`: простого переименования сущности недостаточно, нужно проверить владельца ресурса, закрытие, восстановление и ограничения истории.

Основные [модули Git](https://github.com/pingdotgg/t3code/blob/337c5858c33bc7f8f6dfd391a2c279fa0f7e4d17/apps/server/src/git/GitManager.ts) и [терминалов](https://github.com/pingdotgg/t3code/blob/337c5858c33bc7f8f6dfd391a2c279fa0f7e4d17/apps/server/src/terminal/Manager.ts) просмотрены через граф кодовой базы. Полный аудит их транзитивных зависимостей входит в этап 0.

Не переносим агентский event sourcing, историю разговоров, облачную учетную запись, мобильный клиент, удаленную инфраструктуру и провайдеры моделей ради получения Git-кнопки. Если конкретный верхнеуровневый компонент тянет весь агентский домен, берем его нижележащую операцию и UI-примитивы. Обработка ошибок и проверки безопасности при этом сохраняются.

Сохраняем уведомления об авторских правах и лицензии переносимых частей. У T3 Code [MIT-лицензия](https://github.com/pingdotgg/t3code/blob/337c5858c33bc7f8f6dfd391a2c279fa0f7e4d17/LICENSE); зависимости и ресурсы требуют отдельного учета.

## 3. Технологическая основа

| Слой | Предлагаемый выбор | Причина |
|---|---|---|
| Desktop | Electron, TypeScript | Требование пользователя; использование готовой оболочки T3 |
| UI | React, Vite/Vite+, Tailwind, Base UI | Совместимость с исходными компонентами и быстрая локальная загрузка |
| Состояние | Атомы/точечные подписки из выбранной базы T3; локальное состояние для меню и форм | Изменение одного терминала не должно инвалидировать весь проект |
| Навигация | TanStack Router, если сохраняется при извлечении UI | Проекты и worktree имеют устойчивые адресуемые состояния |
| Backend | Отдельный Node-процесс; Effect для переносимых сервисов и их жизненного цикла | Отделение работы ОС от renderer; единая модель отмены и ресурсов |
| Контракты | TypeScript + runtime-схемы из выбранного транспорта T3 | Проверки IPC/RPC на границе, явные ошибки и версии |
| Редактор | Monaco ESM, только необходимые языковые модули и workers | Готовые модели документов, undo, selection, multi-cursor и IDE API |
| Python intelligence | Pyright language server; Ruff для lint/format/code actions | Готовые анализаторы в отдельных процессах |
| Git | Системный Git через существующий сервис/драйвер | Поведение worktree, hooks и credentials соответствует инструментам пользователя |
| Терминалы | `node-pty` + выбранный терминальный renderer T3 | Настоящая shell, TUI, ANSI, Ctrl+C, независимый процесс |
| Поиск | `rg` как дочерний процесс, пакетная выдача результатов | Нет необходимости писать собственный полнотекстовый движок |
| Хранилище | Одна локальная SQLite-БД, минимальный драйвер из выбранной основы | Транзакционное сохранение сессий и черновиков без серверной БД |
| Тесты | Vitest, Playwright Electron, целевые интеграционные тесты с настоящим Git | Проверка поведения в desktop-приложении и воспроизводимых нагрузок |

[Monaco](https://github.com/microsoft/monaco-editor) предоставляет редактор, но не превращает приложение в VS Code: LSP-клиент, файловые операции, Python-окружения и навигацию интегрируем отдельно. VS Code extensions не считаем совместимыми автоматически. Выбор Monaco проверяем в этапе 0 на времени ввода, undo, LSP и памяти; не пишем собственный редактор для экономии размера библиотеки.

[Pyright](https://github.com/microsoft/pyright/blob/main/packages/pyright/package.json) поставляет `pyright-langserver`. Для Ruff используем актуальный [встроенный `ruff server`](https://docs.astral.sh/ruff/editors/). Pylance не закладываем как обязательную зависимость. Версии всех инструментов фиксируются после рабочего среза; обновление не должно незаметно менять диагностику проекта.

Python backend для самой IDE не нужен: Python запускается как инструмент и пользовательский процесс. Отдельный Rust-сервис рассматриваем только при доказанном профилем узком месте; уже существующий нативный терминальный движок можно сохранить.

## 4. Архитектура процессов и владение данными

Минимальная схема: Electron main → renderer рабочего окна и отдельный workspace backend. Backend владеет файловой системой, Git, хранилищем и запусками. Pyright, Ruff, Git, `rg` и PTY работают дочерними процессами. Worker редактора и worker diff не выполняют тяжелые вычисления на потоке UI. Встроенные веб-страницы размещаются в изолированных WebContentsView.

Electron main обслуживает окна, меню, системные диалоги, protocol handlers, keychain и запуск backend. В нем нет обхода дерева репозитория, расчета diff, Python-индексации и синхронного сохранения больших JSON.

Renderer владеет фокусом, раскладкой, текущими вкладками и моделями редактора. Ни один нажимаемый UI-контрол не ждет ответа GitHub, Git или SQLite, чтобы показать свою реакцию. Длительная операция получает `operationId`, состояние выполнения и отдельное сообщение о результате.

Backend — единственный владелец записей на диск и реестра процессов. В нем используется асинхронный I/O; тяжелый CPU parsing не маскируется под async-функцию и уходит в worker. Падение language server не завершает терминалы и не закрывает редакторы.

Стартуем с одного renderer на рабочее окно и одного backend на экземпляр IDE, а не с окна и Node-процесса на каждый worktree. Дополнительные окна могут подключаться к тому же владельцу ресурсов. Редактирование одного файла из двух окон требует проверки версии при сохранении.

Локальный транспорт сначала сохраняет проверенную границу T3: типизированный RPC и подписки. Если это loopback WebSocket, слушаем только loopback, проверяем случайный токен экземпляра, origin и доступ к операциям. IPC не считается автоматически быстрее: заменять транспорт на MessagePort имеет смысл только после измерения. Терминальные байты и текст документов не проходят через общий React-store.

### 4.1. Минимальная структура репозитория

```text
apps/
  desktop/                 Electron main, preload, упаковка
  web/                     React/Vite renderer
  server/                  workspace backend
packages/
  contracts/               runtime-схемы, команды, события, ошибки
  shared/                  необходимые чистые функции из T3
  source-control-core/     только используемый контракт хостинга
  source-control-github/   адаптер GitHub
tests/
  electron/                сквозные пользовательские сценарии
  fixtures/                генераторы репозиториев и нагрузок
```

Внутри renderer достаточно feature-папок `projects`, `worktrees`, `editor`, `files`, `surfaces`, `island`, `git`, `terminals`, `lineage`, `pull-requests`. В backend соответствуют сервисы workspace, files, Git, process, language и storage. Не создаем отдельный пакет и интерфейс на каждый класс.

Минимальные `sessionId`, document generation и surface lifecycle (`attach/detach/dispose`) фиксируются до редактора на этапе 2. Surface view не владеет жизнью документа, PTY или LSP. Этап 8 объединяет UI уже существующих контрактов и не меняет задним числом владельцев ресурсов.

## 5. Модель проектов и worktree

| Сущность | Идентичность и владение |
|---|---|
| Project | Пользовательская точка входа: имя, локальная папка/корни, закрепление, настройки действий |
| Repository | Локальный Git common directory, remote и сведения репозитория; общий для связанных worktree |
| Worktree | Отдельный checkout с собственным корнем, HEAD и index; ветка — изменяемое свойство |
| WorkspaceSession | Стабильный ID сессии worktree: вкладки, раскладка, Lineage, интерпретатор, терминалы |
| Document | Ключ сессии и нормализованный URI; текст, версия, dirty, disk baseline и состояние восстановления |
| Surface | Типизированное содержимое вкладки: editor, diff, terminal, browser или pull-request |
| ActionDefinition | Определение запуска в проекте, без изменяемого состояния выполнения |
| ProcessRun | Конкретный запуск с sessionId, actionId, cwd, PTY, временем, статусом и портами |
| NavigationEntry | Сессия, документ/URI, диапазон, символ и контекст позиции |
| GitOperation | Целевой worktree, исходные refs, выбранные файлы, фазы и подтвержденные результаты |

Ветка не является ID: ее можно переименовать, удалить или переключить извне. Путь тоже не единственная идентичность: внешний диск может исчезнуть, worktree — переместиться. Сохраняем ID и сверяем путь с Git metadata; при неоднозначности предлагаем повторно привязать папку, не склеиваем записи автоматически.

Одинаковый `src/models.py` в двух worktree — два разных документа, две undo-истории и два набора диагностики. Ключи cache, LSP requests, файловых событий, diff и Git-операций включают session/worktree и версии. Кэш GitHub дополнительно учитывает host, repository, PR number, пользователя и SHA.

Проект без Git открывается как обычная Python-папка, с отдельной файловой сессией. Git-раздел предлагает инициализацию. Чтение и редактирование файлов не зависят от наличия GitHub-учетной записи.

### 5.1. Жизненный цикл сессии

| Состояние | Что остается в памяти и что работает |
|---|---|
| Active | Видимые поверхности, модели открытых документов, текущие подписки, Python intelligence |
| Warm | Недавно использованные модели/состояние, ограниченный кэш дерева и Git; без отрисовки скрытых панелей |
| Cold | Метаданные, сохраненные черновики и раскладка; language server и тяжелые модели освобождены |

Работа пользовательских процессов учитывается отдельно: cold-сессия может иметь запущенный Django и сохранение логов. Усыпление UI не посылает SIGSTOP пользовательским процессам.

Начальный лимит прогрева — активная сессия и две недавно использованные. Это стартовая политика для измерений, не обещание одинаковой памяти для любых Python-проектов. На первом шаге держим language server активной сессии и максимум одной предыдущей; меняем лимиты по данным. Явно закрепленная нужная сессия может остаться прогретой, но не отменяет лимитов памяти.

Dirty-документы сначала надежно сохраняются как recovery draft. Не освобождаем единственную копию текста до подтверждения записи. При выгрузке модели сохраняем текст, selection и scroll; полноценный undo гарантируется для прогретой модели в текущем процессе. Сохранение undo через выгрузку/перезапуск отдельно проверяется возможностями редактора, не подменяется обещанием восстановления текста.

Выгрузка dirty-модели имеет состояния SnapshotPending → Durable → Evicted. Незавершенных выгрузок одновременно не более двух; модель и ее snapshot учитываются в лимите до подтверждения durable-записи. При disk full, timeout или неоднозначном результате записи модель остается в памяти, дальнейший прогрев останавливается, освобождаются чистые модели и кэши. Выбор сессии и ее каркас остаются доступны; чтение нового документа при исчерпанном лимите явно отклоняется с действиями Save/Export/Discard по выбору пользователя. Уже принятый текст не отбрасывается. Это ограниченный degraded mode: обещание загрузить cold-документ за 300 мс не действует при отказе хранилища/исчерпании лимита, а причина видна сразу.

### 5.2. Переключение worktree

1. Фиксируем view state текущего редактора и целевой sessionId.
2. Сразу меняем активный контекст, восстанавливаем закэшированные вкладки, фокус, дерево и остров.
3. Подключаем уже существующую модель открытого файла либо асинхронно восстанавливаем ее из recovery/disk.
4. Подписываемся на актуальные данные сессии и запускаем проверку дискового состояния.
5. Прогреваем Python intelligence и необходимые поверхности по приоритету.
6. Поздние ответы прежней сессии обновляют только ее кэш. Ответы устаревшей версии документа отбрасываются.

В этой цепочке нет `git checkout`, `git fetch`, полного обхода файлов, ожидания терминала или обязательного запуска LSP. Быстрое A → B → C не должно дождаться загрузки B, чтобы показать C.

### 5.3. Создание и удаление worktree

Создание: выбираем base ref и имя ветки, проверяем имя через Git, выполняем `git worktree add`, регистрируем путь и открываем сессию. Установка зависимостей и создание venv — отдельные видимые операции, не условие показа редактора. Уже созданные Git worktree обнаруживаются через `git worktree list --porcelain -z`.

Git обычно не позволяет одной ветке одновременно быть checkout в двух worktree. Если ветка уже открыта, переключаем пользователя в имеющуюся сессию; `--force` не используем как обход. Detached HEAD отображаем явно. Эти ограничения следуют [модели Git worktree](https://git-scm.com/docs/git-worktree).

Удаление проверяет dirty buffers, index, untracked/ignored пользовательские данные и запущенные процессы. Действие удаления дисковой папки явно отделено от «убрать из недавних» и «закрыть сессию». Используем Git-команду удаления, не рекурсивный `rm`; не удаляем главную рабочую папку как linked worktree. Не запускаем prune/cleanup при временном отключении внешнего диска.

Для проектов вида `vist` с вложенными репозиториями дерево показывает репозитории как отдельные Git-корни. Остров получает явный repository selector и не выбирает случайный repo по последнему открытому файлу. В v1 worktree создается для выбранного репозитория; согласованная смена веток десятков вложенных репозиториев не считается атомарной операцией и не выполняется скрыто.

## 6. Бюджеты отзывчивости

Измеряем packaged release build с production renderer; DevTools и dev server выключены. Исходная референсная машина для согласования — MacBook на Apple Silicon с 16 ГБ памяти и локальным SSD. Отдельно измеряем проект на внешнем SSD: путь пользователя указывает на такой сценарий. Конкретную модель CPU, refresh rate, Electron/Node версии и файловую систему записываем в отчет.

| Сценарий | Начальная цель p95 | Дополнительный критерий |
|---|---:|---|
| Ввод символа → видимое обновление редактора | ≤ 32 мс | p99 ≤ 50 мс; без потери ввода и IME |
| Открытие меню/палитры, визуальная реакция кнопки | ≤ 50 мс | Backend не участвует в реакции |
| Смена вкладки с загруженной моделью | ≤ 50 мс | Без повторного чтения файла |
| Переход в warm-worktree → восстановленный редактируемый документ | ≤ 100 мс | Цель улучшения — 50 мс; фокус и позиция верны |
| Переход в cold-worktree → каркас с верным контекстом | ≤ 100 мс | Редактор с обычным файлом до 300 мс на reference workload |
| Открытие файла до 200 КБ на локальном SSD → доступный текст | ≤ 100 мс | На холодной ОС-кэш и внешнем диске фиксируем отдельные результаты |
| Палитра → первые результаты из прогретого индекса имен | ≤ 100 мс | Новые результаты приходят пакетами |
| PTY output → видимый терминал при умеренном потоке | ≤ 50 мс | При flood допускается отставание с ограничением памяти |
| Первый экран небольшого diff из кэша | ≤ 150 мс | Остальные файлы загружаются отдельно |
| Холодный старт приложения → доступный экран проектов | ≤ 1,5 с | Проверяем и настоящий холодный запуск, и повторный |
| Восстановление последнего проекта с обычным файлом | ≤ 2,5 с | Без ожидания LSP, сети и полной индексации |

Время клонирования, fetch/push, создание venv, готовность Django и полный анализ Python не получают фиктивной гарантии 100 мс. Их UI получает немедленную реакцию, прогресс, доступный лог и корректную отмену там, где она возможна.

Для кадров: ориентир 60 FPS на 60 Гц и проверка на 120 Гц. Бюджет кадра — 16,7 мс и 8,3 мс соответственно; собственная работа обработчика UI обычно должна занимать до 4 мс. Не заявляем, что p95 ввода 32 мс означает 120 FPS. В целевых сценариях не должно быть длинных задач renderer > 50 мс из нашего кода; причины задержек Chromium/GPU фиксируем отдельно.

Предварительный бюджет RSS всех процессов IDE: пустое окно до 300 МБ; один обычный активный Python-проект до 800 МБ вместе с его language servers; десять зарегистрированных worktree при ограниченном прогреве до 1,2 ГБ. Это гипотезы этапа 0, которые проверяем и корректируем явно. Пользовательские Django/pytest и тяжелая веб-страница учитываются отдельными строками, чтобы не скрывать итоговую память машины. Память Pyright сильно зависит от проекта.

Idle-цель для IDE без пользовательских задач — менее 1% одного CPU core в среднем за 60 секунд, после окончания служебной работы. Тестируем утечки на 500 переключениях сессий и 100 открытиях/закрытиях поверхности. Memory plateau означает ограниченный дрейф и наклон на всей измеряемой серии по алгоритму §15.4, а не допустимые 10% прироста после каждого цикла.

## 7. Правила реализации быстрого UI

1. Текст, selection, undo и terminal screen хранятся в редакторе/терминальном движке. React получает события dirty, diagnostics summary, title и статус, а не копию всего текста на каждую клавишу.
2. Компоненты подписаны на нужные сущности и поля. Событие одного ProcessRun не перерисовывает дерево, PR и редактор. Общий Context не переносит весь workspace snapshot.
3. Дерево, поиск, timeline и большие diff виртуализированы; в DOM находится viewport с небольшим overscan. Файловый backend тоже ограничивает выдачу: виртуализация DOM не оправдывает загрузку всего репозитория в память.
4. Только видимые панели получают подробные live streams. Для фоновых worktree нужны компактные статусы, а не полные GitHub timelines и terminal snapshots.
5. Сначала показываем имеющееся состояние, потом обновляем. Устаревшие GitHub/Git сведения помечаем; черновой commit не рисуем успешным до подтверждения.
6. Отмена и защита от устаревших ответов обязательны для поиска, LSP, diff и переключения. Каждая операция несет sessionId и generation/version. Одного AbortController недостаточно, если дочерний процесс уже отправил ответ.
7. Очереди разделены по приоритетам: ввод и открытие файла; пользовательская навигация; обновление видимых данных; фоновая индексация и prefetch. Количество одновременно работающих Git/rg/LSP-задач ограничено, а очередь объединяет повторные запросы.
8. Потоки терминала, файловых событий и поиска имеют backpressure, ограниченные буферы и пакетную доставку. События статуса можно объединять до последнего; терминальные control sequences нельзя произвольно выбрасывать.
9. Monaco, diff, PR и browser-модули грузятся при необходимости. Экран проектов не импортирует весь редактор и все интеграции на старте.
10. Resize проходит через ResizeObserver и один layout на animation frame. Не читаем и не записываем геометрию вперемешку в цикле.
11. Сквозной request/operation ID позволяет связать UI timing, RPC и backend, без логирования содержимого файлов и секретов.
12. Автоматическую мемоизацию и ручные `memo/useMemo` выбираем по выбранной базе T3 и профилю. Не добавляем их в каждый компонент. Если сохраняем React Compiler и upstream lint, следуем их контракту.

Для backend и main запрет на блокирующий I/O относится и к логированию, SQLite-записям и JSON parsing. Рекомендации согласуются с [руководством Electron по производительности](https://www.electronjs.org/docs/latest/tutorial/performance): откладывать ненужную загрузку и проверять реальные узкие места профилем.

### 7.1. Стартовые лимиты и насыщение

Числа ниже — начальная конфигурация для spike и нагрузочных тестов. Лимиты действуют на экземпляр IDE суммарно по окнам, кроме явно указанных per-resource. Перед увеличением лимита повторяется соответствующий benchmark. У каждого ресурса один владелец учета; «освободить слот» означает дождаться завершения/подтвержденного закрытия, а не только отменить Promise.

| Ресурс | Начальный cap | Насыщение, отмена и освобождение |
|---|---|---|
| Модели и recovery snapshots | 80 обычных моделей; 128 МиБ текста в UTF-16 и копий snapshots суммарно; до 3 прогретых сессий | Удаляем чистые LRU-модели и выключаем prefetch. Dirty eviction только после Durable. Новое чтение/большая вставка, превышающие доступный бюджет, отклоняются до аллокации; существующий текст сохраняется. Учет реального heap/RSS дополняет, а не заменяет лимит текста |
| Recovery writer | 1 worker, до 2 in-flight snapshots и 8 pending записей метаданных; snapshot-копии включены в лимит выше | Для документа оставляем последнюю версию pending, не накапливаем копии текста. Checkpoint maxWait 2 с от старейшей неподтвержденной правки не сдвигается вводом/coalescing (§13.2). Возраст неподтвержденной правки > 3 с либо I/O без ответа > 5 с включает degraded mode; нового writer поверх зависшего не создаем и запись не считаем успешной. Ресурс удерживается до подтвержденного завершения/закрытия worker; старый snapshot не может затереть новую версию |
| Python servers | До 2 прогретых LSP-сессий; до 1 стартующей, startup deadline 15 с | Последний запрос прогрева заменяет устаревший pending. Завершение ненужного сервера освобождает слот после exit; до восстановления overlays semantic actions показывают Warming. После deadline — typed error и ограниченный retry, ввод продолжает работать |
| Служебный Git | 2 локальных read-процесса: 1 слот зарезервирован для foreground; до 16 pending, по одному последнему status на worktree | Фоновая работа не занимает резерв. Status deadline 5 с, diff metadata 15 с; при timeout завершаем process group, после 1 с эскалация. Только exit освобождает слот. Commit/hooks — отдельная пользовательская операция, не этот read pool |
| Сетевой Git/GitHub | До 2 сетевых операций и 16 pending; локальный writer не удерживается между сетевыми шагами | Устаревшие refresh удаляются. HTTP deadline 30 с, push/fetch inactivity deadline 120 с с видимым продлением пользователем. Timeout запускает reconciliation, не повтор мутации; доступ к файлам/локальному commit другой сессии не блокируется сетью |
| Поиск `rg` | 2 процесса, из них 1 foreground; до 8 pending, один актуальный поиск на UI-контекст; выдача до 5 000 совпадений/4 МиБ | Новая строка поиска отменяет старую process group; pending заменяется. Deadline 10 с для первой выдачи, остановка по лимиту с признаком truncated и предложением сузить запрос. Выдача пакетами; отмененная выдача не попадает в UI |
| IPC/RPC data plane | Кадры до 64 КиБ; до 1 МиБ pending control-данных, 2 МиБ terminal-данных на PTY и 8 МиБ суммарно | Control и terminal data имеют отдельные bounded каналы; output не блокирует Stop/Save. Статусы coalesce, bulk-read передается с credit/ack. Raw PTY → parser приостанавливает read по credit; display patches можно заменить новым bounded screen snapshot с generation/sequence, без потери состояния parser |
| Пользовательские PTY | До 12 запущенных; история до 8 МиБ/5 000 строк на PTY и до 64 МиБ суммарно; отдельный cap canonical parser states 64 МиБ | Уменьшаем старую scrollback, не режимы текущего экрана. Новый Run сверх cap отклоняется с предложением остановить выбранный процесс; старые не убиваются ради admission. При нехватке parser budget ограничиваем новые terminal/resize; фактическая native/WASM memory измеряется. State освобождается после PTY exit/закрытия parser handle |

Foreground file reads используют отдельные 2 I/O-слота и до 8 pending reads; устаревшие открытия заменяются, deadline 5 с переводит запрос в ошибку без повторной аллокации поверх не завершившегося I/O. Они не ждут Git/rg. Pending control queue резервирует 64 КиБ для Stop/Cancel и сохраняет их при coalescing, а отсутствие свободного слота сообщает немедленно. Если foreground-операция не может стартовать из-за cap, она получает видимый queued/rejected status, а не неограниченное скрытое ожидание.

Нельзя гарантировать неограниченное редактирование при disk full и конечной RAM. На пределе действуют отказ новой аллокации и сохранение уже принятого текста: возможная вставка отклоняется целиком с объяснением, а не обрезается. Проверка такого отказа, recovery после освобождения места и отсутствие скачка памяти входят в acceptance, отдельно от нормальных latency budgets.

## 8. Поверхности и взаимодействия

### 8.1. Экран проектов

Берем информационную структуру стартового окна PyCharm: компактный список, имя, путь, поиск и основные действия сверху. Применяем светлую палитру Superfluid. В левой колонке достаточно Projects, Recent и Settings; SSH, плагины и маркетинговые разделы в v1 не нужны.

Строка проекта показывает имя, сокращенный путь и компактный summary: последний worktree, число запущенных процессов, локальные изменения при наличии кэша. Раскрытие показывает связанные worktree и их ветки. Worktree не засоряют основной список как независимые дубликаты одного проекта, но их можно закрепить для прямого входа.

Поиск сначала фильтрует загруженные имена и пути. Навигация — стрелками, Enter открывает, Escape очищает или возвращает фокус. Контекстное меню предлагает закрепление, Reveal in Finder и удаление записи из списка. Удаление записи не трогает файлы.

Open использует системный folder picker. Clone предлагает URL и целевую папку, показывает прогресс и не блокирует список. New Python Project создает только выбранную папку и минимальный стартовый файл; создание окружения — явный следующий шаг, без скрытой установки пакетов.

Недоступный внешний диск отображается как недоступный проект с действием повторного подключения. Не обнуляем сессии и не удаляем recovery drafts. Большой список проектов виртуализирован; Git-статусы запрашиваем для видимых и недавно активных записей, а не для всех на каждом открытии.

Приемка: открытие экрана работает без сети; поиск и выбор доступны до завершения проверки путей; добавление другого checkout того же repo не создает случайную копию существующей worktree-сессии.

### 8.2. Основная раскладка проекта

Верхняя полоса: проект, активный worktree/ветка, быстрый переключатель и палитра команд. Worktree должен быть постоянно различим, особенно когда два окна открывают одинаковые пути относительно разных checkout.

Слева дерево. По центру основная группа редакторов. Справа по запросу вторая группа поверхностей со своими вкладками. Остров привязан к рабочей области и показывает контекст активной сессии. Каждая поверхность имеет явный sessionId; при смене активной группы остров не должен незаметно перенаправить действие на другой репозиторий.

По умолчанию обе группы принадлежат одному активному worktree. В v1 сравнение двух worktree выполняется отдельным действием diff или быстрым переключением; постоянное смешивание редакторов разных worktree в одном наборе вкладок откладываем, чтобы исключить двусмысленность Save/Run/Commit.

Исходные размеры для макета: sidebar 260 px с диапазоном примерно 200–480; правая группа от 360 px; остров около 260 px. Это дизайн-значения для проверки на реальном контенте, а не контракт backend. При недостаточной ширине правая группа занимает основную область или скрывается по явной кнопке, не сжимая код до непригодной ширины.

Перетаскивание вкладки меняет группу без закрытия документа. Открытие diff/PR справа оставляет центральный файл и позицию. Разделитель поддерживает мышь, клавиатуру и сброс пропорции. Восстанавливаются ширины, открытые вкладки, выбранная поверхность, фокус и дерево для каждой сессии.

### 8.3. Дерево проекта

Два основных режима: Project и Changes. Первый показывает структуру файлов, второй — только измененные файлы с их родительскими каталогами. Смена режима сохраняет отдельные selection, scroll и раскрытые узлы; закрытие diff возвращает предыдущий режим, если пользователь сам не выбрал другой.

Каталоги читаются при раскрытии. Для огромной папки нужен поток/порции и ограниченный сортировочный кэш, а не получение сотен тысяч записей одним IPC-ответом. Сначала поддерживаем раскрытие, сворачивание, single-click preview, double-click pin, создание, rename, delete и Reveal in Finder.

Иконки и Git-badges показывают статус файла, а для папок — агрегат уже известных данных. Диагностика и Git не запускают рекурсивный обход при каждом render. Компактные папки и скрытие excluded directories настраиваются как предпочтения отображения, не через изменение файлов проекта.

`.venv`, `.git`, `__pycache__`, `.mypy_cache`, `.ruff_cache`, build и известные кэши исключены из тяжелого фонового анализа. Отображение скрытых/ignored файлов включается отдельно. Пользователь может открыть файл напрямую, даже если он исключен из индекса поиска.

Один backend watcher на активный корень используется несколькими потребителями. События объединяются и инвалидируют только затронутые каталоги/документы/Git-сведения. Не ставим один watcher на каждую строку дерева. События `.git` учитывают общий Git directory и per-worktree metadata. При пропуске событий, sleep/wake и возвращении фокуса выполняется ограниченная reconciliation-проверка.

Symlink показывается как ссылка; не обходим циклы и не начинаем watch всего диска через ссылку за корень. Открытие внешней цели требует отдельной разрешенной файловой области. Rename обновляет вкладки, URI, recovery и Lineage согласованно; при ошибке имя и содержимое остаются доступными.

### 8.4. Редактор с вкладками

Базовый набор: Python highlighting, номера строк, indent guides, выделение парных скобок, multi-cursor, undo/redo, find/replace, go-to-line, word wrap, выбранная кодировка/line endings и открытие по traceback. Monaco подключается непосредственно к моделям документов, без контролируемого React `value` на каждую клавишу.

Single-click в дереве открывает preview-tab. Повторный выбор заменяет чистый preview; редактирование или double-click закрепляет вкладку. Dirty preview никогда не исчезает при выборе другого файла. Повторное открытие того же документа выбирает уже существующую вкладку.

На каждую видимую группу — один активный editor instance; документы представлены моделями и view state. Не создаем по Monaco на каждый файл, на каждую строку PR или на каждый скрытый worktree. При переносе поверхности сохраняем модель и undo, пересоздаем только view при необходимости.

Первичная подсветка доступна без ожидания type checker. Completion, hover, signature help, go to definition/type definition/implementation, find references, document symbols и rename приходят через LSP. Для нескольких определений показываем компактный список. References открываются во второй поверхности либо в компактном списке с переходом.

Python-рефакторинг в v1 ограничен поддержанным LSP rename с preview списка затронутых документов и согласованным применением WorkspaceEdit (§9.2). Если сервер не гарантирует корректность операции или файл вне разрешенного корня, показываем причину; не заменяем semantic rename глобальной заменой строки.

Файлы большего размера, первоначально от 2 МБ или 50 тысяч строк, открываются с отдельным large-file режимом: без тяжелых semantic tokens, minimap и автоматической полной диагностики. Точный порог устанавливается benchmark. Для очень больших и бинарных файлов показываем ограниченный preview с возможностью открыть системным приложением; не загружаем гигабайты в text model.

Приемка: одинаковый файл в двух worktree сохраняет разные изменения; A → B → A возвращает selection/scroll/undo прогретой модели; Python completion не блокирует ввод; IME, emoji, кириллица и вставка большого блока не теряют текст.

### 8.5. Плавающий остров

Остров — компактная панель часто используемых действий с группами Scripts, Git, Servers/Terminals, Lineage. В исходном состоянии он расположен у нижнего края рабочей области с зарезервированным безопасным местом. Остров можно свернуть и закрепить у края, чтобы он не перекрывал курсор, diff и completion popup.

Перемещение ограничено границами workspace; позиция сохраняется. При узком окне сворачиваем остров в компактный контрол с popover. Не прячем единственную кнопку остановки процесса внутри hover-only интерфейса. Свернутый остров сохраняет счетчик активных процессов и доступ к разворачиванию с клавиатуры.

В строке Git всегда видна ветка выбранного repository/worktree. Статусы загрузки/ошибки занимают стабильное место, не меняя высоту при каждом ответе. Большое количество процессов и длинный Lineage получают собственный ограниченный список, не растягивающий остров на весь экран.

Здесь нет weekly usage, модели агента и общего ресурсного процента из T3: эти сведения не описывают задачу Python IDE. Системные метрики, если понадобятся, появятся отдельным инструментом после измерений.

### 8.6. Универсальная поверхность справа

Для начала достаточно конечного набора `editor | diff | terminal | browser | pull-request`. Общий контракт содержит surfaceId, sessionId, kind, заголовок, ресурс и сериализуемое view state. Runtime handles, редактор и PTY в сохраненную раскладку не сериализуются.

Кнопка «+» и палитра показывают доступные типы. Поверхность можно выбрать, закрыть, перенести в другую группу, развернуть или восстановить. Закрытие view не равно закрытию ресурса: terminal остается запущенным, документ остается dirty, PR draft остается в хранилище.

Browser открывает явно выбранный URL или URL запущенного action. Используем изолированный WebContentsView, запрещаем доступ к API IDE, обрабатываем permission requests и навигацию. Разрешаем localhost HTTP для development; внешние адреса и открытие системным браузером проходят проверку схемы. Вкладки браузера ограничены по ресурсам, скрытые приостанавливают лишнюю активность там, где это не ломает задачу.

Overlay-меню и диалоги должны правильно перекрывать нативную веб-поверхность: WebContentsView имеет отдельный жизненный цикл и геометрию, поэтому перед показом модального UI проверяем порядок/видимость. Это отдельный риск раннего рабочего среза.

После перезапуска браузер восстанавливает URL, а не JavaScript-состояние страницы. External links и файл-вложения PR не получают Node-доступ. Не подключаем IDE bridge к удаленной странице ради удобства.

## 9. Python-окружения и навигация

### 9.1. Интерпретатор на сессию

Определяем кандидатов без запуска произвольного кода проекта: явный выбор пользователя, локальная `.venv`, сведения `pyproject.toml`/`pyrightconfig.json`, затем доступные системные интерпретаторы. Для неоднозначного случая показываем короткий selector с путем и версией.

Команды Poetry/uv/Conda используются только по запросу либо через проверенный путь выбранного окружения. Не запускаем hooks, `setup.py` и неизвестные shell-функции для простого открытия проекта. Создание `.venv` и установка зависимостей доступны как явные действия с логом.

По умолчанию новый worktree получает собственную `.venv` или явно выбранный существующий интерпретатор. Не копируем venv как обычную папку и не подменяем его symlink автоматически: пути и зависимости могут отличаться между ветками. Shared interpreter возможен как осознанный выбор пользователя.

Session runtime получает cwd, путь интерпретатора, environment variables и настройки import resolution. Это один источник контекста для LSP, Run и pytest; не меняем `process.cwd()` или глобальное окружение всего backend при переключении ветки.

### 9.2. Language server

У активных Python-сессий независимые LSP connections и контекст корней. Начальный безопасный вариант — отдельный Pyright-процесс на прогретую Python-сессию. Один общий сервер на все worktree с разными venv не принимаем без доказанной изоляции unsaved overlays и конфигурации.

Порядок открытия: отображение текста → didOpen с актуальной версией → локальная диагностика и completion. Не открываем в LSP все файлы репозитория сами. Полную background-диагностику делаем отключаемой; начальный режим сфокусирован на открытых файлах. Ruff и Pyright получают раздельных владельцев diagnostics и code actions, чтобы не дублировать сообщения и форматирование.

Каждый старт/перезапуск LSP создает новый `lspGeneration`. До состояния Ready восстанавливаем overlays — актуальный несохраненный текст всех логически открытых dirty-документов этой сессии, включая выгруженные модели с durable recovery. Сначала фиксируем набор URI/версий, последовательно отправляем didOpen, затем накопленные didChange и sync barrier; новые правки включаются в этот же барьер. Чистые документы открываем по потребности. UI не ждет барьера для печати, но не выдает семантические результаты по старым дисковым версиям как актуальные. Если dirty overlay невозможно прочитать в пределах ресурсного cap, intelligence остается Warming/Error; потерянный overlay не заменяется диском молча.

didClose отправляется при логическом закрытии документа с Save/Discard; освобождение Monaco-модели ради RAM само по себе не означает отказ от несохраненного overlay. Draft, оставленный пользователем для продолжения работы, остается логически dirty до явного Save/Discard. Requests, diagnostics и responses прежнего lspGeneration игнорируются после restart, даже если sessionId и URI совпали. Повторная загрузка холодной сессии не восстанавливает старый connection handle.

Изменения документов отправляются инкрементально, если сервер это поддерживает. Completion/hover для старой позиции отменяются; диапазоны и правки проверяются относительно версии документа. При медленном LSP редактор остается доступным, а статус intelligence объясняет задержку.

При смене интерпретатора обновляем конфигурацию и при необходимости перезапускаем только сервер этой сессии. При падении — ограниченные попытки restart с задержкой и доступным логом; crash loop не грузит CPU и не обнуляет документы.

WorkspaceEdit применяется одним согласованным изменением buffers, а не последовательностью независимых Save. До preview фиксируем URI, версии открытых моделей и disk baselines закрытых файлов; проверяем allowed roots, кодировку, edit ranges/position encoding, отсутствие пересечений и достаточный бюджет моделей/rollback snapshots. Для versionless edits по закрытому файлу baseline подтверждается повторно непосредственно перед применением. Неизвестные resource operations create/rename/delete, если они не реализованы безопасно в v1, отклоняют весь edit с причиной.

После подтверждения пользователя повторно сверяем все версии и baselines. При любом несовпадении ни одна часть не применяется — требуется новый preview. Под короткой блокировкой participating documents готовим все новые buffers и before-images, затем публикуем изменение без await между документами; ввод и LSP-события ставятся после этой локальной операции. Ошибка применения откатывает buffers по before-images, не затрагивая диск; listeners не получают половину транзакции. Результат помечает документы dirty и связывает их общим edit ID для диагностики/undo. Последующее сохранение файлов независимо и не обещает атомарности файловой системы между несколькими файлами. Если до применения нельзя получить эксклюзивное владение изменяемыми buffers другого окна, операция отклоняется целиком.

### 9.3. Lineage

Lineage — линейная история смысловых переходов по коду: definition, implementation, references selection, symbol search и traceback. Обычные движения курсора и каждое нажатие стрелки не добавляют элемент.

До перехода сохраняем исходный URI, диапазон, selection и scroll. После успешного разрешения сохраняем цель и имя символа. Запись выглядит как `OrderService → BaseService → Repository`; доступно Назад/Вперед и выбор конкретного шага. Начальный лимит — 100 переходов на сессию.

Назад восстанавливает предыдущую позицию без нового запроса LSP и без добавления второго события навигации. Новый переход после Назад отсекает forward-часть. Соседние одинаковые переходы объединяются. Истории worktree независимы и не смешиваются после переименования ветки.

Для редактируемого документа используем tracked ranges редактора. Для восстановленной записи после изменения файла проверяем символ и короткий локальный контекст, затем предлагаем ближайшую допустимую строку. Удаленный файл отмечается недоступным; не перескакиваем на одноименный файл другого worktree. История не требует собственного глобального графа классов.

## 10. Скрипты, Django и долгоживущие процессы

### 10.1. Определение действия

Минимальные поля: id, имя, тип, команда/аргументы, относительный cwd, keybinding, environment overrides и необязательный preview URL. Типы начала: Shell command, Python file/module, Django server. Значения по умолчанию привязаны к активной сессии и выбранному интерпретатору.

Определение ActionDefinition принадлежит проекту и может иметь override сессии, например порт. ProcessRun всегда принадлежит конкретной сессии. Одно действие Test можно одновременно запустить в двух worktree, получив два независимых терминала и статуса.

Обычная shell-команда выполняется в настоящем PTY. Введенная пользователем shell-строка сохраняет ее shell-семантику; мы не пытаемся разбить ее пробелами в argv. Типизированные Python/Django-действия строят argv без конкатенации непроверенных значений в shell-команду.

Форма использует референс Add Action: имя, shortcut, команда, preview URL. Дополнительно доступны cwd и env в раскрываемой части. Поля «перед запуском агента», «когда thread settles» отсутствуют. Автозапуск при создании worktree — опциональное явно включаемое поведение только для доверенного проекта, не дефолт.

На экране Run сразу появляется создаваемый ProcessRun со статусом Starting; это еще не Running. Повторный клик для уже запускаемого singleton Django открывает его терминал. Повторный запуск обычной команды можно выполнить в новом терминале через явное действие.

### 10.2. Модель выполнения

Состояния: Starting → Running → Stopping → Exited/Failed. Для сервера readiness хранится отдельно: running-процесс еще может не слушать порт. Exit code и signal сохраняются; Ошибка запуска отличается от завершения команды с ненулевым кодом.

Есть Stop, Restart, Rename terminal, Reveal output и Open preview. Сначала мягкая остановка process group, затем после разумного timeout — явная принудительная остановка. Учитываем Django autoreloader и дочерние процессы: убийство одного PID может оставить рабочий сервер. На macOS это проверяется настоящим интеграционным тестом.

Переключение worktree, закрытие вкладки и сворачивание острова не прекращают запуск. Закрытие проекта предлагает конкретное действие для работающих процессов. Полное Quit IDE в v1 останавливает принадлежащие ей процессы с понятным выбором при закрытии. Работа после полного Quit или падения backend требует отдельного supervisor/daemon и не обещается первым релизом.

При падении renderer backend и PTY продолжают работать, новое окно подключается повторно. При падении backend не объявляем старые PID активными по сохраненной записи: PID может быть переиспользован. После запуска проводим reconciliation и показываем прерванный запуск с доступным логом; произвольный shell нельзя восстановить из истории вывода.

### 10.3. Django

Поля пресета: interpreter, `manage.py`, settings module, bind host, port, env и preview URL. Команда стартует в корне выбранного worktree. Без особой настройки используем localhost, а не публикацию на все сетевые интерфейсы.

Для двух параллельных worktree предлагают разные порты. Пробная проверка свободного порта лишь подсказка: гонка остается до фактического bind. При конфликте показываем ошибку процесса и быстрый выбор другого порта. Readiness определяем через явно настроенный health URL/TCP probe; URL из лога — кандидат для открытия, а не доказательство готовности.

Git worktree изолирует файлы, но не базу данных, Redis, Docker volume и внешние сервисы. В action можно задать отдельные env/порты для worktree. Автоматически выполнять migrations или менять конфигурацию общей БД при создании ветки нельзя. Копирование `.env` и credentials — только явное действие пользователя.

### 10.4. Именованные терминалы и поток вывода

Остров показывает серверы и терминалы вместе с короткими именами: `Django · :8001`, `pytest`, `Shell`, `Celery`. В строке видны состояние и сессия, при необходимости exit code. Пользователь может привязать URL к терминалу вручную.

Привязка терминала в v1 означает именованную PTY-сессию, которой владеет backend IDE. Подключение к произвольной уже работающей shell во внешнем Terminal.app не обещается: для этого нужен поддерживаемый внешний multiplexer/протокол, одного PID недостаточно.

У каждого PTY один непрерывно работающий canonical terminal parser в отдельном worker workspace backend. Используем Ghostty VT/WASM, но перенос parser за границу renderer и подключение drawing/input adapters — новая проверяемая адаптация Superfluid, не уже готовая гарантия T3. Worker живет столько же, сколько PTY, продолжает разбирать вывод скрытого worktree и владеет текущими main/alternate screen, курсором, modes и ограниченным scrollback. Размер viewport ограничен 400 колонками × 120 строками; resize сверх cap получает явное ограничение. Нативная/WASM память учитывается в §7.1.

UI не пересоздает parser при attach. View получает bounded screen snapshot с `terminalGeneration`/sequence и затем display patches; input/key encoding обрабатывается относительно тех же canonical modes. Эти данные идут непосредственно в drawing adapter, React получает только metadata. Reconnect после падения renderer подключается к тому же backend parser. Переполнение очереди patches инвалидирует только view-generation: отправляется свежий snapshot, старые patches не применяются. Не требуется сериализовать внутреннее состояние Ghostty и восстанавливать его проигрыванием обрезанного ANSI-tail.

Текстовая история T3 ограничена 5 000 строками/8 МиБ и полезна как лог, но tail не сохраняет полный экран и режимы parser. Для пользовательского scrollback храним ограниченные уже разобранные строки canonical parser; plaintext/ANSI log — дополнительная bounded история, не источник восстановления TUI. Постоянный полный лог на диск — отдельный opt-in с ротацией. Исходная реализация истории описана в [terminal runtime T3](https://github.com/pingdotgg/t3code/blob/main/docs/internals/terminal-runtime.md).

Raw ANSI проходит parser ровно один раз. При высоком потоке сначала coalesce display patches, затем применяем credit/backpressure между PTY и worker; raw ANSI до parser не выбрасывается. Скрытые view не отрисовываются. Запросы терминала, требующие ответа shell, обрабатываются единственным живым parser, а display snapshot/replay не создает таких ответов. После crash canonical worker/backend полного восстановления живого TUI из tail не обещаем: показываем потерю terminal state и предлагаем явный restart, сохраняя доступный лог и не объявляя его эквивалентом восстановленного экрана.

Gate этапа 0 — доказать получение bounded screen/modes и управление input через выбранный ABI без блокировки UI и без повторной эмуляции во view. Если ABI/адаптер это не позволяет, терминальная архитектура считается неподтвержденной: до основной разработки выбирается проверяемый вариант и повторяется тот же тест. Условная фраза «возьмем snapshot T3» не заменяет этот результат.

## 11. Git, изменения и единая кнопка публикации

### 11.1. Обновление состояния

Git-истина находится в Git, а не в optimistic UI. Локальный статус и удаленная информация независимы. Working tree изменяется быстро и обновляется событиями/инвалидацией; fetch, ahead/behind и GitHub checks имеют отдельные кэши и явные состояния stale/offline.

Статус читаем машинным форматом `status --porcelain=v2 -z` с поддержкой rename, untracked и конфликтов. Пути с пробелами, Unicode, переводом строки и ведущим дефисом не разбираем по строкам shell-output. Дочерние процессы получают cwd и argv явно, для путей используем `--`.

Не считаем добавленные/удаленные строки по всему repo при каждом изменении символа. В острове сначала доступно число файлов; статистика строк поступает из ограниченного фонового запроса. У больших/binary diff показываем причину отсутствия статистики, а не неверный ноль.

Изменяющие локальные Git-фазы сериализуются по области общих ресурсов репозитория; стартовый вариант — один локальный writer на repository внутри IDE. Блокировка охватывает подготовку index/commit и обновление локальных refs, но не всю составную операцию и не ожидание push/HTTP. Сетевые операции имеют отдельные слоты (§7.1), так что медленный push A не держит локальный commit B. Чтения ограничены отдельно. IDE-lock не защищает от внешнего Git: проверки до запуска уменьшают гонки, а сверка результата и состояние Uncertain предотвращают автоматическую публикацию неподтвержденного результата. Невозможность эксклюзивно блокировать произвольный внешний Git не скрывается.

### 11.2. Changes и diff

Нажатие Changes открывает diff во второй группе и переводит sidebar в Changes. Из редактора можно быстро вернуться к файлу; из diff — к его текущей строке. Отдельные режимы: unstaged против index, staged против HEAD и изменения ветки относительно выбранной base. Для ветки обычно нужен merge-base/triple-dot, а не сравнение только tips; режим подписан явно.

Не смешиваем локальные несохраненные buffers с Git diff молча. Показываем «есть несохраненные файлы» и предлагаем сохранить их перед пересчетом/commit. Для diff между buffer и disk используем отдельный локальный режим.

Первый экран загружает список файлов и видимый diff, остальные — по мере прокрутки/раскрытия. Поддерживаем unified/split, сворачивание контекста, переход к следующему изменению, бинарный статус, rename и крупный diff с ограничением. Не создаем сотни Monaco diff editor одновременно; для review сохраняем специализированный diff renderer.

Конфликт Git отображается отдельно, а не как обычное изменение. В v1 даем открытие конфликтного файла и статуса; полноценный трехсторонний merge editor — следующий самостоятельный этап. Пока конфликт не разрешен, commit/push-последовательность не продолжает работу как будто ветка готова.

### 11.3. Commit → Push → Create PR

Одна основная кнопка запускает последовательность; раскрывающееся меню позволяет выполнить каждую операцию отдельно. Зависимые шаги не выполняются одновременно: PR должен ссылаться на успешно опубликованный commit. Диалог подготовки запоминает сообщение, выбранные файлы, remote, head и base; повторный запуск не требует заполнять все заново.

1. Проверяем конкретный sessionId, repo, HEAD, dirty buffers, конфликты, remote и выбранную base. Смена активного UI после запуска не меняет цель операции.
2. Показываем состав commit: staged и выбранные unstaged/untracked. По умолчанию не включаем новые файлы автоматически и не выполняем `git add .`. Уже staged чужие файлы учитываются явно: пользователь либо принимает весь index, либо меняет staging до запуска.
3. Stage выбранных целых файлов — первый объем v1; hunk staging можно добавить позднее. Подтверждаем конкретное index tree OID и перечитываем HEAD/symbolic ref перед commit. Эта проверка не является межпроцессной транзакцией; итог commit тоже сверяется. Незавершенные изменения index не откатываем слепо при ошибке.
4. Выполняем commit с пользовательскими hooks, signing и identity. Логи доступны в поверхности операции. После выхода проверяем parent/tree/ref и фиксируем commit OID; hook, изменивший состав commit, требует нового подтверждения перед публикацией. Отмена или сбой между Git и журналом переводят фазу в reconciliation, а не означают, что commit отсутствует.
5. Публикуем immutable подтвержденный OID в явный destination ref: семантика `git push <remote> <OID>:refs/heads/<branch>` без force. Remote/repository/ref зафиксированы в операции; перед запуском сверяем локальный контекст, но последующее внешнее продвижение branch ref уже не подменяет source SHA push. При необходимости настраиваем upstream только для явно выбранных локальной ветки/remote; fork и upstream могут быть разными репозиториями.
6. Проверяем существующий PR по GitHub repository/head/base. Если он уже есть, открываем его. Если нет — создаем с выбранным заголовком, описанием и режимом draft, затем показываем ссылку и PR-поверхность.

UI показывает фазы: Preparing, Committing, Pushing, Creating PR, Completed/Failed/Cancelled и Uncertain/NeedsReview. После доказанно успешного commit и неуспешного push повтор предлагает Push; после push и ошибки создания PR — Create PR. При отсутствии новых локальных изменений шаг commit можно явно пропустить, подтвердив существующий OID.

Для защиты от двойного нажатия/переподключения используем operationId, локальную запись фаз и проверку фактического Git/GitHub результата. GitHub API не обеспечивает произвольный exactly-once для всей цепочки: после неоднозначного network timeout сначала ищем уже созданный PR, не отправляем повторное создание вслепую.

### 11.4. Доказательства фаз и восстановление Git-операции

До первой мутации сохраняем durable intent: operationId, session/worktree identity и canonical Git dirs, исходные symbolic branch ref/HEAD, утвержденное index tree OID, выбранные пути, GitHub host/repository ID, remote URL identity, destination ref и base/head repository/ref для PR. Remote и symbolic ref при resume сверяются заново, не берутся из текущего UI. При повторной подготовке изменившееся дерево index требует нового preview/подтверждения.

| Фаза | Условия и сохраняемое доказательство | Reconciliation после сбоя/отмены |
|---|---|---|
| Prepared | Intent записан; target identity, HEAD/ref и утвержденное дерево совпали | Если отличаются — NeedsReview до любых мутаций. Никакого автоматического checkout/reset |
| CommitIntent → Committed | До Git записан CommitIntent с parent/tree; после exit сохраняются exit status, наблюденные reflog records и найденный commit OID с проверенными parent/tree, ref и контекстом операции | При потерянном подтверждении изучаем reflog/кандидатов между исходным и текущим состоянием, используя метку operationId там, где Git ее поддерживает. Одного текущего HEAD или совпадения сообщения недостаточно для атрибуции. Единственный доказанный результат можно записать; неоднозначный — Uncertain с обнаруженными commits, без повторного commit и без автоматического отката |
| PushIntent → Pushed | Persist подтвержденного source OID, remote/repository identity, destination ref и наблюденного remote OID; push использует явный refspec; сохраняются transport status и remote ref после операции | После timeout сначала проверяем remote. Точное совпадение с source OID подтверждает нужное состояние; отсутствие результата позволяет предложить повтор push того же OID после сверки. Другой remote OID — NeedsReview; не force-push и не принимаем чужой head за свой |
| PRIntent → PRLinked | Persist head/base repo+ref, утвержденного source OID, title/body/draft; после ответа сохраняем PR ID/URL и head OID | После timeout ищем existing PR с точной парой repo/ref. При нескольких/недоступном результате — Uncertain. При head OID, отличном от подтвержденного, — NeedsReview, без повторного создания и без автоматического закрытия найденного PR |

Внешний процесс может поменять index/ветку между последней проверкой и самой Git-командой. Поэтому план гарантирует остановку перед дальнейшей публикацией при неожиданном результате, а не невозможность появления неожиданного локального commit. Проверяем tree/parent созданного commit, не сбрасываем чужую ветку/index и показываем пользователю фактический результат. Если доказательство принадлежности commit операции отсутствует, безопасный исход — остановка, а не догадка по HEAD.

GitHub PR ссылается на подвижную ветку: нельзя атомарно зафиксировать remote head между проверкой и HTTP Create PR чужими блокировками. Проверяем head OID ответа/повторного чтения; изменение приводит к NeedsReview с понятным описанием. Это исключает ложный Completed, но не обещает невозможный exactly-once/неподвижный head при внешних авторах.

Без сети commit остается доступен, push и PR показывают ожидаемую ошибку с сохраненным контекстом. Force push, автоматический rebase и автоматический merge в эту кнопку не входят. При rejected push предлагаем отдельное решение, не меняем историю автоматически. Commit message и PR description не требуют AI-провайдера.

## 12. Поверхность GitHub PR

### 12.1. Общая модель

Шапка содержит repository, номер, заголовок, автора, состояние, head/base, статистику файлов и checks summary. Вкладки Summary, Timeline и Code независимы по загрузке и scroll. Открытие PR не запускает checkout и не изменяет файлы.

Summary показывает Markdown-описание, reviewers, labels, checks и комментарии. Timeline — commits, reviews, обсуждения и изменение состояния. Code — список измененных файлов, выбор all commits/конкретного commit, unified/split и сворачивание контекста. Сообщение о пустом списке отличается от loading/error; skeleton из референса — только временное состояние.

Используем минимальный адаптер GitHub, по возможности из T3, а не абстрактный универсальный хостинг на десятки провайдеров. Внутренний контракт уже может иметь provider/host, чтобы позднее добавить GitLab, но v1 реализует и тестирует GitHub. Self-hosted GitHub Enterprise не считается покрытым автоматически.

### 12.2. Данные и сетевые задержки

Быстро показываем последнюю сохраненную шапку и Summary с отметкой времени. Body, timeline pages, checks details и patches приходят отдельно. Запросы дедуплицируются, используют доступные conditional requests и backoff при rate limit. Polling только для видимого открытого PR, реже в фоне; закрытые вкладки не создают бесконечные запросы.

Diff-кэш привязан к base/head SHA и выбранному commit, не только к номеру PR. Обновление head инвалидирует patches и привязки строк. Для больших PR поддерживаем paging файлов; ограничения API, truncated patches, бинарные файлы и недоступные commits отображаем явно с переходом на GitHub. PR в сотни файлов не загружается одним гигантским ответом.

Если локально доступны нужные Git objects, code diff можно построить по точным refs; отсутствие объекта не запускает скрытый checkout пользовательской ветки. Fetch для review выполняется явно/фоном с видимым статусом, без замены рабочего дерева.

### 12.3. Обсуждения и действия

Первый рабочий срез — чтение всех трех вкладок и переход в локальный код. Затем добавляем общий комментарий и draft inline comments с явной кнопкой публикации. До отправки drafts живут локально и изолированы по repo/PR/head SHA. Начальная интерактивность PR не должна зависеть от загрузки review-формы.

Inline comment хранит commit, old/new path, сторону и диапазон diff. Если head изменился, не отправляем комментарий на ту же числовую строку без повторной проверки. Outdated comments отображаются отдельно; повторная привязка не должна менять смысл обсуждения.

Approve/request changes и разрешение discussions добавляем только в пределах возможностей перенесенного адаптера и отдельного критерия приемки этапа PR. Merge и управление branch protection в первый релиз не требуются. Любая запись на GitHub начинается с явного действия пользователя; повтор после неясного timeout требует reconciliation, чтобы не дублировать комментарий.

Переход «открыть локально» проверяет соответствие repository, worktree и ревизии. Если файла/ревизии нет, показываем read-only содержимое review либо предлагаем создать отдельный review-worktree. Не меняем текущую ветку автоматически. Для PR из fork не запускаем скрипты и project hooks при простом просмотре.

Markdown описаний/комментариев санитизируется. Ссылки проверяются, изображения и внешние вложения не получают полномочий IDE. Git credentials для push и GitHub API token — разные каналы: используем системный credential helper/SSH и существующую авторизацию `gh` либо keychain-токен, не сохраняем секреты в SQLite/проектном JSON.

## 13. Сохранение, восстановление и границы безопасности

### 13.1. Хранилище

SQLite хранит проекты, связи с worktree, настройки интерпретатора, action definitions, layout, navigation history, recovery drafts и записи длительных операций. Кэш Git/GitHub отделен от пользовательских черновиков: его можно удалить без потери работы. Вывод терминалов хранится ограниченно, отдельно от транзакций раскладки.

В SQLite не попадает каждое перемещение мыши и каждая порция terminal output. Раскладку сохраняем после короткого trailing debounce и на значимых границах; dirty drafts — независимо от layout. Миграции версионированы и транзакционны, перед несовместимой миграцией сохраняется резервная копия. Единственный writer не создает конкурирующие соединения от каждого компонента.

Пользовательские настройки IDE остаются в application data. Разделяемые project actions можно экспортировать в `.superfluid/project.json` со schemaVersion; импорт такого файла не дает автоматического разрешения выполнять команды. Секретные env values остаются локальными или задаются ссылкой на keychain. В v1 достаточно локального хранения actions и явного экспорта: собственная синхронизация настроек не требуется.

### 13.2. Работа с документом

Файл имеет disk baseline: содержимое/хеш и метаданные версии, на основе которых модель была открыта. Сохранение сериализуется по документу. Перед записью сверяем текущую дисковую версию; при внешнем изменении dirty-файла показываем выбор Compare/Reload/Overwrite, не перетираем его незаметно.

Запись использует временный файл в том же каталоге и атомарную замену там, где это корректно для файловой системы, с сохранением существенных прав и line endings. Symlink и hardlink требуют отдельной политики: нельзя заменить ссылку обычным файлом незаметно. Ошибки permission denied, disk full, отключение диска и rename failure оставляют buffer dirty и recovery доступным.

Проверка версии плюс atomic rename не является межпроцессным compare-and-swap: другой редактор может записать файл между ними. Минимизируем окно, проверяем внешние изменения и не обещаем абсолютную блокировку сторонних программ. Оригинальная версия для conflict/recovery остается доступной. Для наших собственных окон один backend сериализует запись.

Format-on-save/organize imports привязаны к версии buffer. Если пользователь продолжил ввод, устаревшая правка не заменяет новый текст. Асинхронное сохранение старой версии не снимает dirty с более новой. Автосохранение на диск — отдельная настройка; recovery drafts включены независимо и не меняют пользовательские файлы.

Для v1 гарантируем UTF-8, BOM и LF/CRLF без незаметного преобразования. При неподдержанной/неоднозначной кодировке открываем предупрежденный read-only preview либо предлагаем явный выбор, не декодируем с потерей байтов и не сохраняем поверх оригинала.

Recovery checkpoint планируется после 300–500 мс простоя, на переходе сессии и с `maxWait = 2 с` от первой правки, еще не покрытой durable snapshot. Непрерывный ввод не сдвигает maxWait: по deadline актуальная версия ставится в уже существующий bounded writer либо coalesce pending-версии с сохранением исходного deadline. Никаких новых writers/неограниченных snapshots ради соблюдения таймера. Для каждого документа храним version и время старейшей еще не подтвержденной правки; ACK старой версии не очищает состояние более новых правок. После ACK запускается следующий deadline для оставшихся изменений, даже если пользователь не делал паузу.

В нормальном профиле предлагаемый durability budget — ACK не позднее 3 с от старейшей неподтвержденной правки. Это цель для исправного хранилища, а не гарантия flush при зависшем диске. Превышение возраста 3 с, отказ admission, disk full или writer timeout немедленно включает описанный degraded mode и показывает возраст последнего durable snapshot. При аварии восстановление гарантирует последнюю подтвержденную версию; очередь и сам debounce durable-записью не считаются. Потеря последних правок ограничена фактическим отставанием от ACK; при отказе хранения этот интервал может быть больше 3 с и не скрывается. Обычное закрытие ожидает подтверждения принятых recovery-записей либо остается незавершенным с явным выбором пользователя. Повреждение кэша не считается причиной удалить черновики.

При запуске сначала показываем доступную shell проекта, затем восстанавливаем активный документ, потом соседние вкладки и фоновые сведения. При различии disk и recovery предлагаем сравнение. Недоступный путь не приводит к записи старого черновика в случайную новую папку с тем же именем.

### 13.3. Изоляция

Renderer: `nodeIntegration: false`, `contextIsolation: true`, sandbox, строгий CSP и узкий preload API. Входные параметры IPC/RPC проверяются на тип, размер, целевую сессию и допустимый путь. Не выдаем универсальный `exec(command)` любому содержимому browser surface. Встроенные веб-страницы и Markdown не могут вызывать filesystem API IDE. Основа — [рекомендации Electron по безопасности](https://www.electronjs.org/docs/latest/tutorial/security).

File API нормализует пути и проверяет область доступа, в том числе traversal, symlink и отсутствующие конечные файлы. Новый путь проверяется через допустимый существующий parent. Git/shell запускаются с явным cwd; вывод дочернего процесса не используется как инструкция выполнить другую команду.

Открытие незнакомого проекта само по себе не разрешает actions, project hooks и автоматическую установку зависимостей. Первый явный Run/включение autostart устанавливает понятную доверенную область. Git hooks работают при запрошенной пользователем Git-операции, но не при чтении дерева.

Локальные логи имеют ограничение размера, ротацию и редактирование чувствительных полей. Содержимое файлов, токены и полный env не включаются в telemetry по умолчанию. Для первого релиза достаточно локальной диагностики и добровольного экспорта отчета производительности.

## 14. Светлая тема, плотность и управление

Основная тема — светлая с нейтрально-серой оболочкой и белой рабочей поверхностью. Начальные токены: shell `#F3F4F6`, editor/surface `#FFFFFF`, secondary surface `#F8F9FB`, border `#D9DDE3`, text `#20242B`, muted `#5E6571`, accent `#245FDB`. Это исходные значения для contrast-проверки; semantic names важнее конкретных hex.

Sidebar серый, редактор белый, активная вкладка отделяется фоном и тонким маркером. Остров белый с нейтральной границей и небольшой тенью. Git-зеленый/красный всегда сопровождаются `+/-`, иконкой или подписью. Ошибки, focus ring, selection и diagnostics имеют различимые состояния. Не переносим темную палитру PyCharm только потому, что она на reference screenshots.

Шрифт интерфейса — системный macOS либо уже используемый Inter, код — выбранный monospace с fallback и корректной кириллицей. Исходные размеры UI 12–13 px, код 13–14 px, строка дерева 24–26 px, tabs около 34 px. Плотность и zoom настраиваются; важны пригодность долгой работы и контраст, а не максимальное число пикселей на экране.

Анимации ограничены opacity/transform примерно 80–120 мс и не задерживают смену контекста. Нет анимированного slide всего редактора при переключении worktree, тяжелого backdrop blur и постоянных декоративных shimmer. `prefers-reduced-motion` поддерживается.

Начальный набор: открыть файл, глобальный поиск, палитра, следующий/предыдущий worktree, последние worktree, toggle sidebar/right surface/island, Run, Stop, Lineage Back/Forward и Changes.

Не перехватываем системные/редакторские команды глобально без контекста.

Поддерживаем focus order, roving tabindex дерева и вкладок, keyboard resize, accessible names и возврат фокуса после закрытия popover. IME composition не запускает горячие клавиши. Во время поиска текстовое поле сохраняет управление вводом; терминал получает свои Ctrl/Alt-комбинации. ## 15. Проверка скорости и корректности

### 15.1. Нагрузочные профили

Нагрузки генерируются воспроизводимыми fixture-скриптами, с зафиксированным seed и без скачивания случайных репозиториев. Содержимое должно напоминать Python-проект: каталоги, импорты, обычные и generated-файлы, ignored venv и конфиги. Набор меняется только вместе с описанием baseline.

| Профиль | Размер и сценарий |
|---|---|
| Small | 1–2 тыс. файлов, 3 worktree, 10 открытых документов, 2 терминала |
| Daily | 10 тыс. файлов, 10 worktree, 30 открытых документов в активной сессии, 4 процесса, видимый PR |
| Large | 100 тыс. файлов, 30 зарегистрированных worktree, ограниченный прогрев, крупный Python import graph |
| Nested repos | Родительский проект с 20 вложенными Git-корнями; раскрытие дерева и явный Git target |
| Diff | 300 измененных файлов/50 тыс. строк patch, затем патологический файл в 10 МБ без переносов |
| Terminal flood | 4 PTY по 100 КиБ/с в течение 5 минут; внутри этого прогона burst 1 МиБ/с на PTY длительностью 5 с с ANSI/Unicode |
| Slow tools | Git задержан, LSP отвечает через секунды, GitHub timeout/rate limit; печать и переключения продолжаются |
| Recovery | Принудительный сбой renderer/backend, disk full, внешний SSD пропал, внешнее изменение открытого файла |

Количество worktree не означает чтение всех их файлов и запуск 30 Pyright. На диске fixtures по возможности используют реальные Git worktree; результаты разделяют физический размер, ignored files и число индексируемых файлов.

### 15.2. Измерения

Для каждого основного действия фиксируем input timestamp, обновление локального состояния, запрос, получение ответа и commit/paint-related события Chromium. `performance.mark` и двойной requestAnimationFrame помогают искать задержки, но сами не доказывают физическое key-to-photon время. Для кадров и ввода используем Electron/Chromium tracing; видео/высокоскоростная съемка — отдельная ручная проверка при сомнениях.

Считаем p50/p95 на минимум 500 повторениях интерактивного сценария после отдельного прогрева; для блокирующего p99 ввода требуется минимум 1 000 событий на прогон. Не используем среднее время трех кликов. Старты измеряем серией независимых запусков; restart процесса и настоящая холодная файловая кэш ОС — разные режимы отчета. Шумные CI-результаты не интерпретируем как точную гарантию пользовательского ввода.

Снимаем renderer long tasks, frame times, число/длительность React commits, backend event-loop delay, IPC payload sizes, число watcher handles, процессы, RSS/private memory, heap и GPU memory, где доступны. Сумма RSS помечается как приблизительная из-за разделяемых страниц; отдельно даем показатели процессов, чтобы уменьшение одного не скрывало рост другого.

Combined Daily длится 10 минут: ввод 4 символов/с, смена worktree каждые 2 с, 4 процесса с логами 100 КиБ/с каждый и запрос status видимой сессии каждые 2 с с coalescing. После отдельного прогрева выполняем прогон без правой панели и прогон с diff/PR справа. Для flood дополнительно работают те же ввод/переключения и 5-секундный burst из таблицы. Latency budgets ввода/меню/warm switch сохраняются во время flood; terminal display lag после burst должен вернуться к умеренному бюджету за 5 с, pending queues не превышают §7.1. Это важнее отдельного красивого benchmark пустого редактора.

### 15.3. Тесты по границам

Unit/component-тесты нужны для нетривиальных переходов сессии, keybindings, stale responses, Lineage, lifecycle операции и сериализации восстановления. Не пишем тесты на каждый статичный div или буквальное копирование реализации.

Git integration использует временные настоящие repo/worktree и локальный bare remote: branch already checked out, detached HEAD, staged/unstaged, rename, Unicode paths, conflicts, commit hook failure, rejected push, внешний commit между фазами, повтор операции и отключение remote. Тестовая identity локальна; production Git config пользователя не меняется.

Fault injection ставит барьеры между проверкой HEAD/index и Git-действием, между успешным commit и durable-записью Committed, между push и Pushed и после принятого GitHub Create PR до получения ответа. Внешний Git в этих точках меняет index, переключает symbolic ref или продвигает HEAD. Проверяем отсутствие автоматического повторного commit/rollback, остановку в Uncertain/NeedsReview и публикацию только зафиксированного OID явным refspec. Медленный push A не блокирует локальный commit B. Detached HEAD получает явное предложение создания именованной ветки/worktree, без добавления скрытого Branch в составную кнопку.

Файловые интеграционные тесты проверяют atomic save, permissions, BOM/CRLF, внешнее изменение, symlink, rename/delete открытого файла, большой файл, ошибку восстановления и сохранение новой версии во время async-format. Никакой failure-path не должен молча объявлять buffer сохраненным.

Recovery scheduler тестируется непрерывным вводом в одном документе 60 с с интервалом 100 мс, без Save, пауз и переключений: maxWait не переносится каждым символом, постановка актуального checkpoint происходит не позднее 2 с, а healthy durable ACK — в пределах 3 с от соответствующей старейшей неподтвержденной правки. В произвольный момент до idle-debounce принудительно завершаем renderer/IDE и после запуска сравниваем восстановленный текст с последней ACK-версией, а не с последней queued-версией. Отдельно задерживаем writer и переполняем очередь: проверяем bounded coalescing, сохранение deadline и своевременный degraded status без ложного ACK. Для логики таймеров используем управляемые часы, для durability/recovery — настоящее хранилище и процессный crash-тест.

Process tests запускают реальный PTY: shell exit, Ctrl+C, process group/reloader, resize, отключение клиента, повторное подключение, bounded scrollback, Unicode на границе chunks и остановка при Quit. Проверяем отсутствие orphan processes после нормального закрытия.

Terminal state test сначала включает alternate screen, cursor/input modes, потом скрывает view и выводит больше лимита истории. Новое view и новый renderer после crash должны получить актуальные screen/modes canonical parser без повторных ответов shell на исторические query sequences. Проверяются lost patches → snapshot resync, resize cap и отказ 13-го Run без остановки первых 12. Crash canonical parser проверяет честное состояние потери эмуляции, не ложное восстановление TUI из tail.

LSP integration использует небольшой настоящий Python-проект с двумя worktree и разными venv/config: completion/definition/rename, unsaved buffer, устаревшая диагностика, перезапуск сервера. Не ограничиваемся mocked ответами, одинаковыми для обеих веток.

Отдельный сценарий: изменить импортируемый `models.py` без Save, выгрузить A, вернуться в A с открытием `views.py` и проверить completion/definition по восстановленному overlay `models.py`, включая правку во время sync barrier. Для WorkspaceEdit rename меняем один из нескольких файлов после preview и проверяем, что ни одна часть не применилась; затем повторяем на согласованных версиях и проверяем все dirty buffers. Ответы прежнего lspGeneration не должны изменять результат.

Saturation tests блокируют recovery writer и заполняют диск, переключают более 20 dirty-сессий и пытаются открыть/вставить текст сверх cap. Проверяют сохранение уже принятого текста, bounded число snapshots, отказ новых аллокаций и возобновление после освобождения места. Зависшие служебные Git/rg занимают background slots; foreground file open/Stop и теплое переключение остаются доступными, процессы после timeout действительно завершаются. Проверяется размер и возврат к норме всех очередей, а не только отсутствие crash.

GitHub contract tests используют сохраненные обезличенные fixtures API: pagination, отсутствующие permissions, fork, existing PR, changed head, truncated patches, timeout и retry. Перед релизом — smoke на отдельном тестовом репозитории и учетной записи; реальные комментарии/PR в пользовательские проекты тест автоматически не публикует.

Electron E2E проверяет полный сценарий: открыть проект → создать worktree → изменить файл → Run → сменить worktree → открыть diff → commit/push в local remote → вернуться к работающему терминалу → Quit/reopen и восстановить draft. Отдельно тестируем GitHub PR через адаптер fixtures.

### 15.4. CI и performance gate

На каждую содержательную правку: форматирование, lint, typecheck, затронутые unit/integration-тесты и Electron smoke. При изменении перенесенных модулей запускаем их upstream-тесты, включая релевантные проверки лимитов потоков и кэшей. Не переносим весь агентский perf suite, если соответствующего домена в Superfluid нет.

На стабильном выделенном macOS runner — release performance suite для Daily. После этапа 0 фиксируем версию reference hardware/profile и budget manifest. Все применимые абсолютные latency budgets §6, RSS/idle cap и queue caps §7.1 — блокирующие критерии release в их заявленных условиях. Превышение абсолютного бюджета дает fail независимо от процента регрессии: 98 → 105 мс при лимите 100 мс — fail, хотя ухудшение меньше 10%. В degraded disk-full/сaturation-сценарии проверяются отдельные правила отказа и сохранения данных, а не невозможная скорость нового чтения.

Относительный сигнал независим: ухудшение > 10% к baseline создает regression alert даже внутри абсолютного бюджета. Повторяем baseline и candidate в одинаковых условиях тремя прогонами, сравниваем медианы соответствующих p95/p99; подтвержденное ухудшение > 10% сверх измеренного шума блокирует изменение. Для абсолютного gate тоже используем три сопоставимых прогона и медиану их соответствующей метрики. При нестабильности runner или недостаточном числе событий результат Inconclusive, не Pass; требуется повтор на стабильном runner. Изменение самих budgets требует явного решения с причиной и новым baseline, а не автоматического обновления snapshot.

Для memory plateau используем 100 warmup-переключений и 20 warmup-циклов поверхностей, затем 5 окон по 100 переключений + 20 открытий/закрытий поверхностей. Активный набор документов, PTY и LSP на границах окон одинаков. После каждого окна — 5 с quiescence и один и тот же диагностический GC для сравнения heaps; обычный latency-run выполняется отдельно без принудительного GC. RSS и WASM/native allocation counters снимаются параллельно, сами по себе heap GC не заменяют.

Первый post-warmup checkpoint — M0. На всех пяти окнах отдельно для heap, accounted native/WASM и RSS требуется: суммарный рост относительно M0 не более меньшего из 5% M0 и 20 МиБ; линейный положительный наклон не более 0,02 МиБ на composite cycle (одно переключение плюс соответствующая доля surface-цикла); рост более 1 МиБ в каждом из трех последовательных окон — fail даже до суммарного cap. Все handles/subscriptions и число процессов возвращаются к исходному активному набору. Это воспроизводимый критерий обнаружения утечки в заданной серии, не доказательство отсутствия сколь угодно малой утечки на бесконечном времени.

Nightly/перед релизом: Large, Terminal flood, memory plateau, sleep/wake, offline и recovery. Артефакты — trace, summary метрик и контекст железа. Сохраняем результаты отвергнутых оптимизаций, чтобы не повторять их. Подход к ограниченным payload и отдельным output streams можно перенять из [performance regression checks T3](https://github.com/pingdotgg/t3code/blob/main/docs/internals/performance-regressions.md).

## 16. Порядок реализации

Этапы поставляют законченные пользовательские сценарии. Производительность проверяется на каждом, а не отдельным финальным спринтом. Оценки ниже — инженерные рабочие дни одного опытного разработчика при переиспользовании исходников; это предварительная оценка, которая уточняется после этапа 0.

### Этап 0. Подтвердить техническую основу — 5–8 дней

Зафиксировать исходный SHA T3 и зависимости. Построить карту импортов кандидатов на перенос, выбрать минимальный buildable набор оболочки/контрактов/терминалов/Git. Проверить лицензионные уведомления, сборку native `node-pty` и Ghostty WASM на macOS arm64.

Собрать один технический экран: Monaco с Python-файлом, две настоящие worktree-сессии, переключение сохраненной позиции, PTY с потоком вывода и минимум Git status. Подключить один Pyright, измерить старт, ввод, переключение и RSS. Проверить изолированный Browser surface с overlay/dialog, чтобы заранее выявить ограничения WebContentsView.

Для терминала доказать архитектуру §10.4: живой canonical parser в backend-worker, bounded screen/modes snapshot, display patches и input при detach/attach; TUI после вытеснения scrollback и renderer reconnect не должен зависеть от проигрывания tail. Замерить CPU/RSS/WASM и задержку backend → drawing adapter. Это отдельная новая адаптация T3 и причина расширенного бюджета spike.

Сопоставить полноценный редактор с редактируемой поверхностью T3. Результат должен обосновать Monaco требованиями undo/LSP/навигации либо показать, что уже существующий движок покрывает их меньшей ценой. Основной план исходит из Monaco; замена требует результатов, не эстетического предпочтения.

Выход: runnable release spike, отчет о зависимостях и baseline, подтвержденный transport, список переносимых модулей с тестами. Gate: terminal state contract подтвержден, а ввод и переключение во время flood укладываются в согласованный budget manifest. Одна гипотеза исправления не считается Pass: после исправления прогон повторяется. Не развиваем все поверхности, пока editor+worktree+terminal срез не прошел gate.

### Этап 1. Оболочка и проекты — 4–6 дней

Создать рабочую структуру, Electron main/preload/backend, светлые design tokens и минимальные UI-примитивы. Реализовать список проектов, search, Open, New Python Project, Clone с прогрессом и недоступный путь. Добавить локальное хранилище, schemaVersion и базовые миграции.

Настроить lint/typecheck/unit и Electron smoke в CI. Добавить локальные performance marks и выпуск development artifact. Системные меню, macOS titlebar/traffic lights, close/quit и keyboard focus должны работать в настоящем окне, а не только в браузере.

Выход: пользователь открывает существующий проект с диска и после перезапуска находит его в списке. Проверка: первый экран не ждет сети и не импортирует необязательные тяжелые поверхности.

### Этап 2. Файлы, редактор и надежное сохранение — 7–10 дней

Сделать lazy/virtualized tree, preview/pinned tabs, document registry и view state. Реализовать чтение/сохранение, dirty state, disk baseline, recovery drafts, external changes, create/rename/delete и базовый поиск файлов/текста. Подключить Monaco workers и правила large-file режима.

С самого начала document/surface registry использует sessionId и generation, даже когда в UI еще только одна сессия; attach/detach не уничтожает ресурсы. Включить admission/eviction и recovery saturation contracts §5.1/§7.1 до многосессионного UI, чтобы этап 3 не переписывал Save/Recovery.

Граница этапа включает обработку disk full/permissions и тесты сохранения старой/новой версии; красивый редактор без этих путей не считается готовым. Restore читает активный документ первым, остальные модели загружает ограниченно.

Выход: можно редактировать небольшой Python-проект, искать код и восстановить несохраненную работу после сбоя renderer. Gate: typing/tab switch/file open на Small и Daily в бюджете, без полного React render на каждую клавишу.

### Этап 3. Worktree как отдельные сессии — 5–8 дней

Реализовать связь Project/Repository/Worktree/WorkspaceSession, обнаружение Git worktree, создание и безопасное закрытие/удаление. Сделать быстрый переключатель, недавние сессии, горячие клавиши и warm/cold lifecycle.

Изолировать документы, раскладку, дерево и recovery по sessionId. Обрабатывать внешнее переименование ветки, detached HEAD, пропавший диск, повторную привязку папки и работу с вложенными Git-корнями. Проверить A → B → C и поздние ответы backend.

Выход: две ветки с одним относительным файлом могут иметь разные несохраненные изменения; переход не выполняет checkout и не ждет Git status. Gate: десять сессий с лимитом прогрева укладываются в бюджет переключения и памяти.

### Этап 4. Python intelligence и Lineage — 6–9 дней

Добавить interpreter selector, обнаружение `.venv`, отдельные LSP connections, Pyright diagnostics/completion/navigation/rename и Ruff format/code actions. Реализовать cancellation, document version checks, server restart и статусы intelligence.

Построить Lineage на событиях навигации редактора: origin/target, back/forward, список символов, restore и недоступные цели. Два worktree с разными интерпретаторами — обязательная интеграционная проверка.

Выход: можно перейти к определению класса, продолжить цепочку и вернуться к исходному месту одним действием. Gate: индексация не ухудшает ввод и переключение, диагностика другой ветки не попадает в активный редактор.

### Этап 5. Actions, терминалы, Django и остров — 7–12 дней

Перенести необходимые ProjectScripts UI и terminal lifecycle. Сделать action form, Run/Stop/Restart, именованные терминалы, контекст окружения и сохранение их метаданных. Добавить Django preset, readiness, URL, порты и process group cleanup.

Довести подтвержденный spike canonical parser/drawing transport до bounded многотерминального runtime; добавить snapshot generations, overflow resync, native/WASM accounting и тесты TUI из §15.3. Это новая адаптация, ее стоимость не скрывается под словом «перенести».

Собрать остров из уже работающих небольших блоков; добавить свернутое/docked состояние. Реализовать foreground metadata и ограничение фоновых потоков. Базовый PTY из этапа 0 должен работать с самого начала; здесь он становится полноценной пользовательской возможностью.

Выход: Django в A и pytest в B работают одновременно, пользователь переключается и возвращается к актуальному терминалу. Gate: flood не вызывает роста очередей без границы и не нарушает input budget, закрытие view не убивает процесс, Quit не оставляет orphan.

После этапов 1–5 получается первая пригодная для ежедневного пробного использования alpha: проекты, редактор, Python, несколько worktree, Lineage и процессы. GitHub PR и полный Git workflow еще не считаются завершенными.

### Этап 6. Git status, Changes и diff — 6–9 дней

Адаптировать Git-сервисы, статус и инвалидацию; показать ветку/изменения в острове. Реализовать вторую группу сначала для diff, Changes tree, staged/unstaged/untracked, выбор base и переход к строке. Добавить файловый staging, commit dialog, обработку hooks/conflicts и крупные patches.

Проверить работу при внешнем `git` и общей metadata нескольких worktree. Нельзя замаскировать устаревший status только skeleton/спиннером — пользователю нужен cached state и корректное состояние ошибки.

Выход: пользователь понимает состав изменений и делает commit выбранных файлов в нужной сессии. Gate: большой diff загружается порциями, Git scan не мешает печати, index не расширяется скрыто.

### Этап 7. Push и GitHub PR — 6–10 дней

Подключить аутентификацию GitHub и выбранный source-control adapter. Реализовать push, upstream/fork/base selection, existing PR detection и составную кнопку с operationId/фазами. Затем добавить Summary/Timeline/Code и нужные кэши/paging.

Добавить общий комментарий и локальные drafts inline review, явную публикацию и обработку changed head. Approve/request changes входят только после отдельной проверки прав и корректной привязки ревизии; создание/чтение PR не должно ждать этой функции.

Выход: commit → push → create/open PR выполняется одним запуском; частичная ошибка позволяет продолжить с нужной фазы. Gate: fixtures timeout/retry не создают повторный commit/PR, сеть не блокирует локальную IDE. Live smoke проводится на специальном тестовом GitHub repo.

### Этап 8. Завершить общую модель поверхностей — 6–10 дней

Объединить editor/diff/terminal/PR через минимальный surface contract. Добавить launcher, перемещение между двумя группами, expand/restore и сохранение layout. Подключить browser, URL процессов, управление ресурсами скрытых вкладок и правильный native z-order.

Проверить focus scopes, контекст острова, однобуквенные launcher shortcuts, выбор документа из diff/PR и корректное восстановление после смены сессии. Не добавлять произвольное docking-дерево только ради универсальности.

Выход: справа можно открыть любой тип поверхности v1 и продолжить редактирование слева. Gate: закрытие вкладок освобождает view/listeners, но сохраняет нужные процессы и drafts; после 100 циклов память стабилизируется.

### Этап 9. Стабилизация, упаковка и релиз — 8–12 дней

Пройти combined load, Large, memory plateau, offline, sleep/wake, внешний SSD и fault injection. Проверить accessibility/focus/contrast, CRLF/Unicode/IME, Git hooks/signing и разрешения macOS. Довести общую надежность Save/Recovery/Stop раньше второстепенных настроек внешнего вида.

Собрать arm64-пакет, подписать и notarize при наличии signing credentials, проверить запуск на чистой машине, native modules, bundled tools и пути к ним. Ключи подписи не нужны для раннего локального spike, но требуются для нормального внешнего распространения macOS-приложения.

Обновление должно сохранять schema compatibility и recovery. Если используем electron-updater, проверяем подписанные артефакты и поведение при незавершенных запусках. Принудительный restart во время работы не разрешается. Подготавливаем короткую инструкцию, экспорт локального diagnostic report и rollback-порядок для данных миграции.

Выход: установочный артефакт, reproducible build, отчет приемки и performance baseline. Windows/Linux переходят в отдельный релизный этап, не отмечаются поддержанными без проверки PTY и упаковки.

### Оценка общего объема

Сумма предварительных этапов — около 60–94 рабочих дней. С резервом 25–30% на связанность T3-компонентов, terminal parser/display adaptation, Electron/native packaging и реальные Python-проекты ориентир составляет примерно 15–25 календарных недель полной работы одного разработчика. Это диапазон планирования, не обязательство по сроку. Пользовательские функции можно выпускать раньше по этапам; полноценный набор v1 оценивается целиком, включая восстановление и производительность.

При необходимости сократить первую alpha оставляем проекты, editor, worktree switch, один interpreter, Run/terminal и локальный diff; форму настройки всех пресетов и расширенный PR review переносим дальше. Ограниченные очереди, надежное сохранение и изоляцию сессий из alpha не вырезаем.

## 17. Основные риски и способ их проверить

| Риск | Почему существенен | Раннее действие |
|---|---|---|
| Высокая связанность T3 UI с thread/orchestration | Перенос одного компонента может потребовать большую часть продукта | Карта импортов и buildable срез на этапе 0; сохранять нижние операции и primitives |
| Память Monaco и Python servers | Десятки worktree легко становятся десятками тяжелых runtime | Лимит прогрева, отдельные бюджеты моделей/LSP, реальные проекты в benchmark |
| Terminal flood | Очередь вывода блокирует transport и обработку других запросов | Независимый поток, backpressure и нагрузка с первого spike |
| Большие деревья и вложенные repo | Полный scan и Git status на каждый каталог создают лавину I/O | Lazy tree, per-root watcher, приоритеты и явный repository selector |
| Потеря данных из-за buffer/disk/index рассинхронизации | У пользователя одновременно IDE, Git и внешние инструменты | Версии, recovery, внешние конфликты и Git reconciliation |
| Django autoreloader и shared services | Процесс продолжает слушать порт; две ветки используют общую БД | Process-group tests, отдельные env/порты, без скрытых migrations |
| WebContentsView | Нативная поверхность перекрывает React overlay, расходует память | Browser/overlay spike, явный lifecycle, ресурсные ограничения |
| Ожидание parity с PyCharm | LSP не воспроизводит все Django/refactoring/debugger возможности | Явный объем Python v1 и реальные navigation/import fixtures |
| GitHub rate limit и нестабильная сеть | PR недоступен или устаревает при обычной работе | Кэш по SHA, paging, stale labels, retry/reconciliation |
| Файлы на внешнем SSD | Латентность, пропущенные события, временная недоступность | Отдельный профиль измерений, reconnect без удаления сессии |
| Обновление upstream | Изменения T3 контрактов и native ABI ломают перенесенные части | Зафиксированный SHA, provenance и тесты при каждом обновлении |

Если целевой бюджет не достигнут, сначала находим виновника в trace. Базовые варианты исправления: уменьшить область подписки, объем данных, число активных ресурсов или синхронную работу. Переписывание всего backend на Rust, замена React и отказ от Electron не являются первым шагом.

## 18. Сквозная приемка первого релиза

1. Открыть/клонировать Python-проект, создать или обнаружить минимум три worktree и выбрать один без отдельного окна на каждую ветку.
2. Изменить одинаковый относительный файл в двух worktree и убедиться, что buffers, Save, diagnostics, Run и undo прогретых моделей изолированы.
3. Запустить Django и pytest в разных сессиях; переключить worktree, закрыть/открыть terminal view и убедиться, что процессы продолжили работу.
4. Перейти к определению класса, затем к другому символу и вернуться через Lineage в исходный документ/позицию.
5. Открыть Changes: получить второй diff и дерево изменений; вернуться в Project tree с прежним состоянием.
6. Сформировать commit из выбранных файлов, опубликовать ветку и создать PR одной последовательностью; отдельно проверить каждый пункт меню и retry после ошибки push.
7. Открыть GitHub PR с Summary/Timeline/Code, checks и обсуждениями; открыть точный файл/ревизию без скрытой смены текущей ветки.
8. Открыть browser/terminal/file/diff/PR справа, изменить размер и перенести вкладку; восстановить layout после перезапуска.
9. Вызвать все основные действия с клавиатуры, сохранить корректный focus и проверить ввод кириллицы/IME.
10. Принудительно завершить renderer, восстановить drafts; проверить disk full, внешний file edit и временно недоступный SSD без молчаливой потери работы.
11. Выполнить Daily combined workload и memory-циклы в packaged build, приложить p95/p99 и traces; зафиксировать все отклонения от предложенных бюджетов.
12. Установить подписанный релиз на чистую целевую macOS, открыть проект без сети и без AI-провайдеров, выполнить редактирование и локальный Run.

До завершения v1 также обязательны saturation/recovery тесты §15.3, TUI reconnect после вытеснения истории, восстановление dirty LSP overlays и отказ всего stale WorkspaceEdit. Git fault injection должен закончиться правильным Committed/Pushed/PRLinked либо явным Uncertain/NeedsReview, без автоматического повторения неоднозначной мутации. Отсутствие этих тестов не компенсируется хорошими метриками пустого редактора.
